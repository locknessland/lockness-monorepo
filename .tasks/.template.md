## 🎓 Guidelines for Using This Template

### When to Create a Task File

- New feature implementation
- Major refactoring work
- Architectural changes
- Breaking changes
- Complex bug fixes requiring multiple files

### How to Fill Out This Template

1. **Start with Overview**: Clearly state what problem you're solving
2. **Define Objectives**: List specific, measurable goals
3. **Map All Files**: Document every file that will be created or modified
4. **Documentation First**: Always plan documentation updates alongside code
5. **Follow GEMINI.md**: Ensure your design aligns with framework architecture
6. **Check STUBS.md**: Identify which stub templates need updates
7. **Plan Tests**: Write test strategy before implementation
8. **Think Migration**: Consider impact on existing users

### Documentation Update Priority

1. **Critical** (must be updated):
   - GEMINI.md (if architecture changes)
   - Package README.md (if API changes)
   - Stub templates (if generated code patterns change)

2. **High Priority** (should be updated):
   - Web docs (`app/view/pages/docs/content/`)
   - LLM docs (`public/llms/`)
   - Root README.md (if core features change)

3. **Medium Priority** (nice to have):
   - Additional examples
   - Video tutorials
   - Blog posts

### Best Practices

- Keep task files focused on a single feature/refactor
- Update the task file as you discover new requirements
- Mark completed sections with ✅
- Add implementation notes as you go
- Reference the task file in commit messages
- Archive completed tasks (move to `.tasks/completed/`)
