# Agentic system audit — 2026-09-04

Review of Lockness's **agentic system**: the sub-agents, skills, and
per-code-brick documentation that let AI agents work on the framework. Measured
against the stated goal: _"a real agentic system where each code brick is
concretely documented and every agent knows what it must do."_

> **Scope note.** `.claude/agents/`, `.claude/skills/`, and `.specnaut/` are
> Specnaut-CLI-managed trees. Improvements to them are recorded below as
> **PROPOSALS**, not edits. Only project-owned surfaces (`docs/`, `deno.json`,
> `scripts/`, `.github/workflows/`) carry directly-actionable backlog items.

---

## Verdict

**This is a strong, unusually mature agentic system — well above the norm.** The
naming/effort conventions, the dual-mode expert seats, the machine-readable
contract family, and the CI-gated per-package briefs are genuinely good
engineering. The stated goal is ~80% met. The remaining 20% is concentrated in
three places: there is **no single map** tying code areas to agents and skills,
**module-level documentation is unenforced** (unlike the package briefs, which
are gated), and **two overlapping workflow families** create ambiguous entry
points. Everything else is polish.

## Current state

### Agents (19 definition files + README)

- **15 Specnaut-bundled agents**, governed by `.claude/agents/README.md`: a
  naming convention (`-expert` = dual review-lens + audit phase; `-reviewer` =
  review-only; `-coordinator`/`-manager` = orchestration; role noun = does the
  work) and an effort convention (all `opus`; `high` floor, `xhigh` only for
  `architect-expert` and `security-expert` whose misses are unrecoverable). The
  rationale is written out and convincing.
- **3 project-local agents** — `architect` (produces design docs),
  `docs-writer`, `package-expert` — living alongside the bundled set but **not**
  covered by the README's naming/effort tally.
- **7 agents carry runbooks** (`developer`, `qa-tester`, `docs-writer`,
  `architect`, `devops-sre`, `code-reviewer`, `product-owner`) and **5 carry
  role memory** (`developer`, `qa-tester`, `security-expert`, `devops-sre`,
  `product-owner`).
- **Contracts are dependency-injected as skills**: `review-findings-contract`,
  `workflow-contract`, `handoff-protocol`, `qa-report-contract`,
  `alert-triage-contract`. This keeps the machine-readable output shapes stated
  once and referenced everywhere.

**Role clarity is high.** Each agent has a crisp "what I do / what I never do"
contract, explicit hand-off targets, and escalation triggers. Tool scoping is
deliberate and correct: read-only lenses get `Read/Grep/Glob/Bash`;
`test-reviewer`'s Bash grant is pattern-scoped to test runners only; `developer`
runs in an isolated worktree with `acceptEdits`; experts are
`disable-model-invocation: true` so they fire only from a review/audit phase.

**Overlap is intentional and well-disambiguated, not accidental:**

- `architect` (writes design) vs `architect-expert` (judges plan/diff) — a table
  inside `architect.md` explains why both exist and warns against merging them.
- `code-reviewer` (line-level pre-merge lens) vs `review-coordinator` (fans out
  lenses, aggregates) — clean separation; the coordinator restates the
  aggregation semantics on purpose (documented, with issue references).

### Skills (37)

Three coherent families plus two workflow families:

- **`*-audit`** (a11y/arch/dep/perf/sec/code/status) — each dispatches the
  matching expert over a resolved scope. Coherent and 1:1 with the `-expert`
  agents.
- **`*-contract`**
  (review-findings/workflow/handoff/qa-report/alert-triage/backlog-*/
  mobile-first/response-style) — preloaded, non-user-invocable machine-readable
  shapes. Well-designed; the reason output stays consistent across seats.
- **Operational** — `board`, `git`, `ship`, `orchestrate`, `specnaut` — each
  with a clear single-owner remit and explicit "who owns what" tables that
  prevent drift.

### Per-code-brick documentation

- **All 28 packages have an `AGENTS.md` brief.** Structure is consistent:
  Invariants, Dependency contract, Public surface, Where to work, Pitfalls,
  Tests, closing gate.
- **Generated blocks are CI-gated.** `deno task agents:brief --check` runs in
  `test.yml`, `publish.yml`, and the pre-push hook. The dependency contract,
  public surface, and test inventory therefore cannot drift from the code.
- **`deps.policy.jsonc`** encodes the binding dependency boundary;
  `deno task deps:analyze` enforces it. `package-expert` is built around staying
  inside that boundary.
- Sampled `packages/session/AGENTS.md` — the hand-written Invariants and
  Pitfalls are excellent (specific, failure-anchored, dated). This is the model
  the whole system should aspire to.

## Findings, ranked by impact

### HIGH-1 · No "code area → agent → skill" ownership map

The user's goal is that _every agent knows what it must do_. Per-agent contracts
answer that from the agent's side. The **inverse** — "I'm about to touch
`packages/auth`; which agent owns it, which review lenses apply, which skill and
docs are relevant?" — has **no single home**. The README covers naming/effort;
each `AGENTS.md` covers one package's internals; but the orchestrator (or a
human) choosing _whom to dispatch for area X_ must assemble that from memory.
This is the single highest-leverage gap against the stated goal. Project-owned
fix (a `docs/` page).

### HIGH-2 · Module-level documentation (hard rule #7) is unenforced

`@fileoverview`/`@module`/JSDoc on public APIs is a hard rule, but there is **no
lint rule, no CI gate, and no coverage check** for it — a sharp contrast with
`agents:brief --check`, which _is_ gated. "Each code brick concretely
documented" at the module/symbol level therefore rests entirely on reviewer
diligence and can silently erode. The package briefs are guaranteed fresh; the
in-code docs they point at are not. Project-owned fix.

### HIGH-3 · Two overlapping workflow families with ambiguous entry points

Specnaut-native (`/specnaut plan|tasks|implement|review`, `/orchestrate`) and a
superpowers-inspired family (`brainstorming`, `writing-plans`,
`executing-plans`, `subagent-driven-development`, `requesting-code-review`,
`verification-before-completion`) both cover discovery→plan→implement→review.
Their trigger phrases overlap (`brainstorming` ⇄ `/specnaut plan` discovery;
`writing-plans` ⇄ `plan`; `subagent-driven-development` ⇄
`implement`/`orchestrate`). The superpowers skills note they are "re-implemented
for Specnaut and integrated with the bundled agents," so this is deliberate —
but **nothing tells an agent which family to reach for when**, raising decision
cost and risking two agents picking different paths for the same work.

### MEDIUM-4 · `security-expert` description under-advertises Mode 3

The frontmatter `description` says "**Three** dispatch shapes" but the
parenthetical lists only two — (1) PR review, (2) alert triage. **Mode 3 (plan
expertise, before any code exists)** is fully specified in the body and is
dispatched by `/specnaut plan`, but it is missing from the description the model
matches against. The cheapest, highest-value security dispatch is the least
discoverable. (Specnaut-managed → proposal.)

### MEDIUM-5 · README conventions omit the 3 project-local agents

The naming table and effort tally (15 agents) cover only Specnaut-bundled
agents. `architect`, `docs-writer`, and `package-expert` fall outside the
documented governance; `docs-writer` has **no `effort:` field at all** (so it
inherits the parent's, undocumented). A reader of the README cannot tell these
three exist or how they are budgeted. (Specnaut-managed → proposal, plus a
project decision on where local agents are documented.)

### MEDIUM-6 · Installed `deno-*` skills are wired into no agent

`deno-expert`, `deno-guidance`, `deno-frontend`, `deno-sandbox`, `deno-deploy`,
`deno-project-templates` are available, yet **no agent references them**. A Deno
framework whose `developer`, `code-reviewer`, and `package-expert` never load
`deno-expert` is leaving domain leverage on the table. (Agent `skills:` lists
are Specnaut-managed → proposal; also depends on whether these plugin skills are
considered project-controlled.)

### LOW-7 · Hand-written brief sections are not gated

Only the _generated_ blocks of each `AGENTS.md` are `--check`ed. `Invariants`,
`Pitfalls`, `Where to work` can be empty or stale with no signal — acceptable by
design (`package-expert` explicitly says an empty section is honest), but a
high-churn package with an empty `Pitfalls` gets no nudge. Consider a soft
warning (not a gate) for packages above a churn/LOC threshold with empty
hand-written sections.

### LOW-8 · `architect` ↔ `architect-expert` disambiguation is one-directional

The distinction table lives only in `architect.md`. `architect-expert.md` does
not cross-link back, so a reader who opens the expert first does not learn the
sibling exists. Minor. (Specnaut-managed → proposal.)

### LOW-9 · No frontend/DB specialist; `developer` is a generalist

There is no dedicated UI-implementation or migration/DB agent — `developer`
covers both, with `ui-ux-designer` (spec only, no code) and
`accessibility-expert` (review only) flanking it. Likely correct for the current
team size; noted for completeness, no action recommended.

## Proposed backlog

> Project-owned items are directly actionable. Items marked **(proposal)** touch
> Specnaut-managed trees and must be raised with Specnaut / applied via
> `specnaut upgrade`, not hand-edited here.

### Epic A — Publish a code-area ownership map · addresses HIGH-1 · size M

- **Write `docs/agentic-ownership.md`** — one table per code area (each
  package + `app/`, `config/`, `.github/`, `scripts/`) mapping area →
  owning/primary agent → applicable review lenses → relevant skill(s) →
  canonical docs. — _the inverse index the system lacks_ — S
- **Link the map from the `AGENTS.md` doc index** so it is discoverable from the
  root. — XS
- **(proposal) Reference the map from `.claude/agents/README.md`** as the "which
  agent for area X" companion to the "how agents are named" doc. — XS

### Epic B — Enforce module-level documentation · addresses HIGH-2 · size M

- **Add a JSDoc/`@fileoverview` coverage check** — a `scripts/docs_coverage.ts`
  that fails when an exported symbol or public module lacks the required tags,
  mirroring the `agents:brief --check` pattern. — _makes hard rule #7 real
  instead of aspirational_ — M
- **Gate it in CI and pre-push** — add to `test.yml` and
  `scripts/install_hooks.ts` alongside `agents:brief --check`. — XS
- **Baseline current gaps; file `tech-debt` tickets** for packages below
  threshold so the new gate lands green. — S

### Epic C — Disambiguate the two workflow families · addresses HIGH-3

- **(proposal) Add a "which workflow" decision table** to the `specnaut` router
  (or a small top-level skill) stating when to use native phases vs the
  superpowers-inspired skills. — S
- **(proposal) Tighten overlapping trigger phrases** in `brainstorming` /
  `writing-plans` / `executing-plans` descriptions so they do not collide with
  `/specnaut plan|implement`. — S

### Epic D — Correct agent-definition drift · addresses MEDIUM-4/5, LOW-8 · (all proposals)

- **(proposal) Fix `security-expert` description** to enumerate all three
  dispatch shapes (add Mode 3 plan expertise) — _the highest-value dispatch is
  currently the least advertised._ — XS
- **(proposal) Extend `README.md` naming/effort conventions** to cover
  project-local agents (`architect`, `docs-writer`, `package-expert`); **add an
  explicit `effort:` to `docs-writer`.** — XS
- **(proposal) Cross-link `architect` ↔ `architect-expert`** disambiguation from
  both files. — XS

### Epic E — Put the `deno-*` skills to work · addresses MEDIUM-6 · (proposal) · size S

- **(proposal) Wire `deno-expert` into `developer`, `code-reviewer`, and
  `package-expert`** `skills:` lists so Deno-specific review knowledge is loaded
  where code is written and judged. — _pending confirmation these plugin skills
  are project-controlled._ — S

### Epic F — Soft-signal stale hand-written briefs · addresses LOW-7 · (proposal) · size S

- **(proposal) Emit a non-blocking warning** from `agents:brief` when a package
  above a churn/LOC threshold has an empty `Invariants` or `Pitfalls` section —
  a nudge, never a gate (empty stays a valid honest outcome). — S

## What is already excellent (keep as-is)

- The `-expert` ⇔ audit-phase naming invariant and the written-out effort
  rationale.
- Dual/triple-mode expert seats sharing one definition (PR review · audit · plan
  expertise).
- Contract-as-injected-skill pattern (`review-findings-contract`,
  `workflow-contract`, …).
- CI-gated generated brief blocks + `deps.policy.jsonc` boundary enforcement.
- `test-reviewer`'s runner-only Bash grant and its two-form evidence standard
  for rule 4.
- The single `package-expert` over 27 near-identical definitions, with knowledge
  living in versioned `AGENTS.md` beside the code.
- `review-coordinator`'s "a seat that returns nothing has NOT passed" arithmetic
  — a genuinely hard failure mode handled rigorously.
